# Held-fixed plus boundary comparison with selected JIST source — 2026-10-08

## Reproduction

```sh
./scripts/compare_plus_boundary_saved_java.sh
```

The script replays the saved 66×76×66 RAS plus crop and verifies the six saved TGDM products, then compiles and executes the preserved JIST `MinFilter3D.java` source under an 8 GB RSS watchdog. The selected source SHA-256 is `ff3f6055325a7b8b488a9a375fa5b6481f8e11bdd4b75376d127d5f937f99daf`.

## Results

On the saved workflow crop, Java and Python boundary outputs are exactly equal, but both are empty (0 foreground voxels). The workflow segmentation contains label 100 as its only label ≥100; candidate boundary voxels touch lower-valued labels and are suppressed by the selected source rule. This is a vacuous result and is not counted as substantive boundary coverage.

On the committed folded synthetic phantom [`segmentation.nii.gz`](../../tests/data/synthetic/plus_boundary_folded_cortex/segmentation.nii.gz), Java and Python are also exactly equal across all 331,056 voxels. Both produce 17,190 foreground boundary voxels. The fixture has neighboring labels 100/101, an inner label 110, low-valued contact 4, and overlooked label 120, so it exercises positive cortical boundaries and the selected suppression/removal rules. Java sampled RSS was 0.083 GB; the saved crop source run sampled 0.080 GB.

## Interpretation

This validates the selected source boundary operation against the Python implementation on a nontrivial synthetic case and records the saved workflow's degenerate boundary case separately. It does not establish the relationship of this adapter to the paper's `mu_boundary` term or full plus-workflow equivalence. The synthetic phantom is generated by [`generate_plus_boundary_folded_fixture.py`](../../scripts/generate_plus_boundary_folded_fixture.py).
