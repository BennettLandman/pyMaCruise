# PyMaCRUISE Porting Plan

This is the step-by-step implementation and acceptance plan for a Python-native MaCRUISE. Work proceeds from source contracts and synthetic cases to stage-by-stage ports, and only then to a small, approved set of real reference cases. Synthetic image volumes, phantoms, and expected outputs created for this project are intended to be committed under `tests/data/synthetic/`; no human imaging data belongs in that directory.

## Completion definition

The port is complete when the base MaCRUISE workflow (T1 + MaSeg) and the selected MaCRUISEplus workflow (T1 + MaSeg/TOADS inputs + FLAIR, as defined by the source entry point) can be installed, configured, run, resumed, and produce documented volume and surface outputs without MATLAB or a MIPAV/JIST JVM runtime. Each stage must have automated checks. Synthetic cases must exercise the contracts and edge cases before reference MRI is introduced. Final equivalence must be assessed against reproducible MATLAB/JIST outputs from approved reference cases, with per-output tolerances, metrics, and any known deviations recorded in the repository.

“Reasonable numerical error” is not one tolerance for every output: exact label/mask operations should be exact; floating-point image stages require measured, operation-specific tolerances; surfaces and thickness require geometric/statistical tolerances. Proposed criteria in the table are minimum gates. Establish and record the final per-stage tolerances against the reference implementation before claiming equivalence.

## Working rules

- Execute rows in dependency order. A row is **validated** only when its stated checks pass and evidence (test name/report, metrics, or source decision) is recorded. Do not fill a validation date before that evidence exists.
- Keep test data synthetic until the Synthetic Readiness Gate. That gate requires fixtures for geometry, label maps, tissue boundaries, bias fields, transforms, surfaces, and lesion cases, and automated tests that pass without downloading or mounting subject data.
- Commit deterministic synthetic input volumes and small expected-result fixtures. Generate large or derivable fixtures in tests when doing so is simpler and deterministic; commit the generator and its seed. Every fixture must have a description, dimensions, spacing/affine, value or label meaning, provenance (synthetic), and license note where relevant.
- Use the MATLAB/JIST wrappers as workflow/parameter contracts and VandyCRUISE as the selected algorithm reference. Reuse NiBabel, NumPy, SciPy, ANTsPy, and scikit-image for general operations where behavior matches. Select mesh I/O/geometry tools only as needed for scientific surface outputs; do not add rendering/viewer tools to the port. Do not substitute a generic algorithm for TOADS, topology correction, ACE, GVF, or CRUISE/TGDM without equivalence evidence.
- Run real-data checks only after synthetic unit/stage gates pass. Use a small, de-identified, approved reference set; do not commit those images or outputs. Record access-controlled locations and hashes/identifiers only where policy permits.

## Real-data gate and data handling

Do not use actual imaging data to fill gaps in ordinary development when the same contract can be tested synthetically. P35 is the required readiness review. Actual MRI is reserved for checking biological realism, whole-workflow interactions, and equivalence to the historical pipeline; it cannot replace deterministic synthetic unit/stage tests. Real cases and derived images stay outside Git unless the user explicitly approves an appropriate, shareable dataset and all applicable data-use requirements are satisfied.
